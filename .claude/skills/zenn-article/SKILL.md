## 適用範囲

このスキルは `articles/<slug>.md` を新規作成・編集する作業全般に自動適用する。ユーザーが「記事を書きたい」「Zenn 記事を作って」「下書き作って」などと頼んだとき、本スキルの規約に従って執筆する。

## 1. 口調

- **である調ではなく、です・ます調で書く。** 砕けすぎず、堅すぎない技術ブログのトーン。
- **一人称は「自分」または省略**。「私」「筆者」「我々」は使わない。
- **断定は事実にだけ使う**。仕様や挙動は断定、感想や運用ノウハウは「〜と思います」「〜が安全です」のように主観であることを明示する。
- **記事のメタ情報を本文に書かない**。「社内 LT 用にまとめた」「登壇で話した」「メモを記事にしました」のような前置きは書かない。記事は単独で読まれる前提で書く。
- **読者を煽らない**。「常識」「当然」「絶対」のような押し付けの語彙は避ける。
- **絵文字は frontmatter の `emoji` だけ**。本文には基本入れない（コードブロックやセクション見出しの装飾目的での絵文字は禁止）。

## 2. 引用元・参考リンクの扱い（最重要）

技術ブログとしての信頼性に直結するので厳格に守る。

- **公式ドキュメントや一次情報からの引用は必ず出典を明示する**。
  - 出典はリンクで示す。例: 「[concepts/multi-agent](URL) では、〜と定義されています」「[channels/discord](URL) の冒頭はこのように始まります」。
  - **NG な言い回し（厳禁）**: 「公式ドキュメントには〜記載があります」「公式ドキュメントには次のように明記されています」「公式ドキュメント上、〜」「公式が掲げている」「公式は〜を推奨しています」「公式の〜」「引用文に書かれている〜」など、**「公式」「引用文」を主語にした文は書かない**。読者から見て冗長で、リンク先のページ名や引用ブロックで十分。引用ブロックを置けば直前で「次のように書かれています」のような前置きも不要。
  - 引用そのものは原文ママ（特に英語）でブロッククォートし、和訳は補足として続ける。
    ```markdown
    > "OpenClaw routes replies back to the channel where a message came from."
    ```
- **公式の用語・固有名詞・パス・コマンド名は原文表記を尊重する**。`agentDir` を `agent_dir` に直す等の改変はしない。
- **一次情報（公式ドキュメント、リリースノート、PR、RFC、issue）を優先**。二次記事・要約記事を引用元にしない。
- **「公式仕様」と「自分の運用ルール」を必ず分けて書く**。
  - 例: スライドや過去の運用にあった `sessions_send` 上限のような取り決めは、公式仕様として混ぜず「運用上の工夫」「自分の運用ルール」として節を分ける。
- **記事冒頭または各章の最後に「参考」セクションで一次情報の URL リストを置く**。

## 3. 最新情報の確認は省略しない

OpenClaw、Next.js、TypeScript、Vitest、Zod など対象が何であれ、**書く前と書いた後に必ず公式ドキュメントを WebFetch で確認**する。

確認ステップ:

1. 記事の対象となる機能・コマンド・設定について、公式ドキュメントを WebFetch する
2. スライドや既存資料との **相違点を必ずリストアップ**する
3. バージョン依存の挙動なら、対象バージョンを明示する（例: 「Vitest 4.0 で追加された〜」）
4. 「at the time of writing」相当の情報は、本文中に「2026-04 時点」のような注記を入れるか避ける
5. 記事に書いた API 名・フラグ名・パスをもう一度公式で grep して、実在することを確認する

「思い出しで書く」は禁止。**過去のメモやスライドが間違っている前提で**最新情報と突合する。

## 4. ディレクトリ構成と命名

```
articles/<slug>.md
images/<slug>/<file>
```

- **slug**: 12〜50 文字、`a-z` / `0-9` / `-` / `_` のみ。意味のある英語の短いフレーズにする（例: `openclaw-multi-agent-routing`）。日付プレフィックスや連番は付けない。
- **画像ファイル名**: 連番 + 内容（例: `01-title.png`, `02-multi-agent-concept.png`）。スペース・全角・記号は使わない。
- **本文中の画像参照は絶対パス**: `/images/<slug>/<file>` 形式。相対パスにしない。

## 5. frontmatter

```yaml
---
title: "記事タイトル"
emoji: "🤖"             # 1文字の絵文字
type: "tech"            # "tech" | "idea"
topics: ["openclaw", "discord", "multiagent", "ai", "agent"]   # 最大5個、英小文字
published: false        # 新規作成時は必ず false
publication_name: "pepabo"   # 必要なときだけ
---
```

- **新規記事は必ず `published: false`（下書き）**。公開はユーザーの明示的な指示があるときだけ `true` にする。
- **タイトル**: 内容を端的に。煽らない。`【保存版】` `〜してみた` のような常套句は避ける（個性として使う場合は除く）。
- **topics**: 最大5個。Zenn のトピック名規約に従い、英小文字・記号なし。
- **publication_name**: 投稿先 publication がある場合のみ指定。個人投稿なら付けない。

## 6. 本文の構成

最低限の骨格:

1. **タイトル画像（任意）** — `![](/images/<slug>/01-title.png)`
2. **対象の概要セクション** — 「○○ とは」のような形で、外部の人が読んでも文脈が分かる導入。**自分や登壇に関するメタ情報は書かない**。
3. **本題のセクション群** — 公式仕様 → 設定例 → 運用上の工夫の順が読みやすい。
4. **参考リンク** — 冒頭または末尾に一次情報の URL を列挙。
5. **まとめ・所感** — 短く。新しい主張を入れない。

セクション見出しは `##`、サブセクションは `###`。`#`（h1）は frontmatter の `title` で代用するため本文では使わない。

## 7. コードブロック

- 言語タグを必ず付ける（` ```bash `, ` ```typescript `, ` ```json5 ` など）。
- JSON のサンプルでコメントを書きたいときは `json5` を使う。`json` でコメントを書かない。
- 長すぎるコードは **要点だけ抜粋** して、フルは GitHub 等のリンクで誘導する。
- ターミナルセッションの貼り付けは、コマンドと出力を分ける。出力に含まれる ANSI エスケープは削除する。

## 8. 画像

- 出典がスクリーンショット系（スライド、ダッシュボード、ライブラリの公式図）の場合、**著作権・利用範囲を確認**する。社外資料の引用は出典明示。
- 画像のキャプションは図の意図を補足するときだけ書く。装飾目的のキャプションは付けない。
- 画像が情報の中核を担うときは、**alt にテキストで内容を書く**（アクセシビリティと検索性のため）。
  ```markdown
  ![Routing は8段階の most-specific wins ルールで決まる](/images/.../06-most-specific-wins.png)
  ```

## 9. 執筆フロー（推奨）

1. ユーザーから題材を受け取る
2. **公式ドキュメントを WebFetch で確認**（複数ページ／関連 issue／リリースノート）
3. **スライド・既存資料との突合表**を作成（このスキルでの必須ステップ）
4. 構成案（章立て・画像・slug・topics）を**ユーザーに提示して確認**
5. 画像を `images/<slug>/` に配置
6. `articles/<slug>.md` を作成（`published: false`）
7. `npm run preview` でローカル確認、`npx zenn list:articles` で認識を確認
8. commit & push
9. Zenn ダッシュボードでデプロイ成功と表示崩れがないか確認
10. ユーザーが OK を出したら frontmatter を `published: true` に変えて再度 push

## 10. 公開前チェックリスト

- [ ] frontmatter の `title` / `emoji` / `topics` / `type` / `published` が正しい
- [ ] slug が 12〜50 文字で命名規約を満たす
- [ ] 画像が `/images/<slug>/` 配下にあり、本文の参照パスが一致
- [ ] 公式ドキュメントへのリンクが本文または参考セクションに入っている
- [ ] 引用ブロックには出典がある
- [ ] 「自分や登壇」に関するメタ情報が本文に残っていない
- [ ] コードブロックに言語タグがある
- [ ] `npx zenn preview` でレイアウト崩れがない
- [ ] `npx zenn list:articles` に出ている
- [ ] 公式仕様と自分の運用ルールが混在していない
- [ ] バージョン依存の記述に対象バージョンの注記がある

## 11. やらないこと

- 公式ドキュメントを確認せずに書く
- 二次記事・ブログ・要約サイトを一次情報のように扱う
- 自分の運用ルールを公式仕様のように書く
- 記事冒頭で登壇・LT・社内勉強会のメタ情報を書く
- `published: true` で新規作成する
- 画像をリポジトリに置かず外部 URL に依存する（`storage.googleapis.com/zenn-user-upload` を除く既存記事はそのまま）
- 絵文字を本文の装飾に使う
- 「絶対」「常識」のような押し付けの語彙
